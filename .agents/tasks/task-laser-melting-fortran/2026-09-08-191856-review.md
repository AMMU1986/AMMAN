# Reassembly of the laser-melting Fortran solver into one gfortran-portable file (v1)

The legacy Fortran 77 SIMPLE/enthalpy-porosity laser-melting solver, which previously depended on `INCLUDE 'PARAM.FOR'` / `INCLUDE 'COMMON.FOR'` and Compaq/DVF intrinsics, was reassembled into a single fixed-form source at `laser_melting/laser_melt.f`. The PARAMETER line and the sixteen COMMON blocks are inlined (PARAMETER first) into all 19 COMMON-using program units; `GETDAT`/`GETTIM` were ported to `DATE_AND_TIME` in `GETIME`; the two diagnostic `PAUSE`s in `ENTRY OUTPUT` became non-halting `WRITE`s; and the one `CALL DENSE` inside the `USER` subprogram (illegal self-recursion into a sibling ENTRY under `-std=legacy`) was replaced with an inline copy of the density loop. The build is clean (`gfortran -std=legacy -ffixed-line-length-132`, exit 0, no warnings) and all acceptance greps pass.

Watch for: the inline DENSE substitution recomputes density only over the interior (2..M2, 2..L2) and drops the `TPI` update, whereas the real DENSE covers the full 1..M1/1..L1 range and writes TPI — numerically inert only because the affected cells and TPI are never consumed downstream (**confirmed**); and the physical constants were placed in a new `COMMON/USRCOM/` block not present in the original COMMON.FOR spec, a deviation from "inline only PARAM/COMMON" that is a benign, arguably necessary, persistence safeguard (**confirmed**).

**Verdict**: APPROVED

## High-level view

The reassembly is mechanically faithful: every routine gets the identical PARAMETER-then-COMMON header, the EQUIVALENCE aliasing of `F`/`FOLD` onto `U/V/PC/P` and `T/TOLD/FACT1/...` is reproduced consistently, and the CALL wiring in `PROGRAM MAIN`, `TIMITR`, and `SETUP2` matches the specified control flow. All 20 named subprograms and every specified ENTRY are present exactly once.

The DENSE-recursion fix is sound. `DENSE` is an ENTRY of `USER`; `OUTPUT` (also an ENTRY of `USER`) originally did `CALL DENSE`, which gfortran rejects as recursion. The inline copy reproduces the density arithmetic verbatim and is numerically equivalent for every quantity read later, because the boundary cells it skips and the `TPI` array it omits are never consumed. Factoring the density loop into a standalone subroutine would be a cleaner long-term structure, but that is style, not a correctness gap.

The four permitted portability edits are correct. `GETIME` uses `DATE_AND_TIME(VALUES=IV)` with the right index mapping and preserves FORMAT labels 10/20/30 and the same-day/cross-day elapsed-seconds arithmetic. The PAUSE→WRITE conversion preserves the diagnostic text and removes only the halt.

The one substantive deviation from the letter of the task is a `COMMON/USRCOM/` block holding the physical constants (DENL, DENS, CPL, ...), which is not in the original COMMON.FOR. Because `USER` is entered through many separate ENTRY calls across the time loop, constants set once in `ENTRY BEGIN` must survive to later `GAMSOR`/`DENSE`/`OUTPUT` calls; a single-routine COMMON guarantees that persistence without changing any numerical value.

### DENSE self-recursion fix and its numerical footprint

`DENSE`, `OUTPUT`, `GAMSOR`, `BEGIN`, `BOUND`, and `OUPT1` are all ENTRY points of the single subprogram `USER`. gfortran under `-std=legacy` treats `OUTPUT`'s original `CALL DENSE` as a recursive call into the same subprogram and rejects it. The fix inlines the density loop directly into `OUTPUT`:

```
         DO 601 J=2,M2
            DO 601 I=2,L2
               DEN1=FACT1(I,J)*DENL+(1.0D0-FACT1(I,J))*DENS
               RHOCP=FACT1(I,J)*DENL*CPL+(1.0D0-FACT1(I,J))*DENS*CPS
               RHO(I,J,1)=DEN1 ... RHO(I,J,5)=RHOCP
```

The arithmetic is identical to `ENTRY DENSE`. Two differences exist against the full DENSE body: the inline loop runs over the interior `2..M2 / 2..L2` rather than `1..M1 / 1..L1`, and it omits the trailing `TPI(I,J)=T(I,J)` loop. Both are inert. `RHO(I,J,1..5)` is only consumed at the `RHO(I,J,5)` read inside `GAMSOR`'s CONVT term, which itself iterates only `2..M2 / 2..L2`, so the skipped boundary cells are never read. `TPI` is written in `BEGIN` and `DENSE` but read nowhere in the file, so dropping its update has no effect. The substitution is numerically equivalent for every consumed quantity. Factoring the loop into a standalone `SUBROUTINE DENSITY(...)` callable from both `USER`'s entries and `SETUP2` would eliminate the duplication, but the inline copy is a legitimate minimal resolution of the gfortran restriction.

### Constant persistence via COMMON/USRCOM

`MAIN` drives `USER` through many separate entry calls: `BEGIN` once, then `GAMSOR`/`DENSE`/`OUTPUT`/`BOUND`/`OUPT1` repeatedly across the `ISTEP` and `ITER` loops. The physical constants (`DENL`, `DENS`, `CPL`, `CPS`, `CMUSH`, `TBOILING`, `EROR`, ...) are set once in `BEGIN` and read in the later entries. Plain local variables are not guaranteed to retain their values between separate invocations of a program unit in standard Fortran, so binding them into `COMMON/USRCOM/` (referenced only inside `USER`) guarantees persistence. The arrays that must also persist — `APSUM`, `TPI` — carry an explicit `SAVE`; `T`/`FACT1`/`RSOLID`/`TOLD`/`FACT1O` persist through their EQUIVALENCE onto the global `F`/`FOLD` COMMON arrays. This closes the persistence question for every cross-entry variable. The only caveat is fidelity: `USRCOM` is not in the authoritative COMMON.FOR and should be recorded as an intentional deviation.

### Header inlining and EQUIVALENCE consistency

Every one of the 19 COMMON-using units carries an identical header: the `PARAMETER(NI=242,...)` line first (so `NI/NJ/NIJ/NFMAX/NZMAX` are defined before the COMMON dimensions reference them), then BLK01–BLK16, then the `U/V/PC/P`, `UOLD/VOLD`, `COF/COFU/COFV/COFP`, and `TH/...` DIMENSION+EQUIVALENCE aliases in consistent order and dimensions across all units, which is what makes the EQUIVALENCE aliasing safe. `DIFLOW` and `GETIME` carry no COMMON. Grep confirms one `PROGRAM MAIN`, 19 PARAMETER headers, and zero remaining `INCLUDE`.

### Verification and unrelated changes

`gfortran -std=legacy -ffixed-line-length-132 -o laser_melt laser_melt.f` compiles clean (exit 0, no warnings). Acceptance greps: `INCLUDE=0`, `PAUSE=0`, `GETDAT=0`, `GETTIM=0`, `DATE_AND_TIME=1`, one `PROGRAM MAIN`, 19 PARAMETER headers. There is no runtime harness or input data in the repo, so behavior beyond compilation is not exercised; the acceptance bar is a clean build, which is met. The commit bundles only the solver, its `.gitignore`, and task-state JSON; no unrelated changes.
